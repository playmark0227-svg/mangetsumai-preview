# 満月米 API（注文・カード決済のサーバー）

オンラインショップ（`shop.html`）と管理画面（`admin/`）を「本番モード」で動かすためのサーバーです。
Cloudflare Workers（サーバー）＋ D1（データベース）＋ Stripe Checkout（カード決済）でできています。

- 商品データを配信し、管理画面からの変更を保存します
- ご注文の金額（商品・送料・合計）を**サーバーで計算し直して**、Stripe の決済画面を用意します
- 支払いが済んだら注文を「支払い済み」にし、在庫を管理している商品は在庫を減らします（決済画面に進んだ分は、支払いが済むか決済画面が閉じられるまで取り置きます）
- 管理画面に注文一覧を返し、対応状況（新規・発送準備中・発送済み・キャンセル）を保存します
- （任意）商品画像を Cloudflare R2 に保存して配信します

カード番号は Stripe の画面でだけ入力されます。このサーバーや当店のサイトをカード情報が通ることはありません。

> サイト側の切り替えは `js/config.js` の `apiBase` だけです。空ならデモモード（今の github.io の動き）、API の URL を入れると本番モードになります。

## しくみ

```
お客さまのブラウザ ── shop.html（GitHub Pages など）
   │  GET  /api/catalog ………… 商品データ（非公開の商品は含まない）
   │  POST /api/checkout ……… 注文内容（金額はサーバーで計算し直す）→ 未決済の注文を保存
   │  POST /api/checkout/cancel … 支払わずに戻ったとき、その決済画面を Stripe で無効にする
   ▼
満月米 API（Cloudflare Workers）──── D1：商品データ・注文　／　R2：商品画像（任意）
   │  Stripe API：Checkout Session（決済画面）を作成
   ▼
Stripe の決済画面 ─ カード入力・3Dセキュア
   │ 支払い完了
   ├─→ Webhook：POST /api/stripe/webhook（署名を確認 → 注文を「支払い済み」に・在庫を減らす）
   └─→ お客さまを shop.html?session_id=…#thanks に戻す → GET /api/checkout/status で結果を表示

管理画面 admin/ ── /api/admin/*（管理用パスワードが必要）
30分ごとの定期処理（cron）── Webhook が届かなかった注文を Stripe に確認して確定・失効させる
```

注文の支払い状態は 3 つです。

| 状態 | 意味 |
| --- | --- |
| 未決済（pending） | 決済画面に進んだが、まだ支払っていない |
| 支払い済み（paid） | 支払いが完了した。管理画面の注文一覧には、既定でこれだけが出ます |
| 失効（expired） | 決済画面の有効期限（既定 30 分。`SESSION_MINUTES`）が切れた・支払わずに戻った・支払いに失敗した・同じご注文を別の画面でやり直した・決済画面を作っている間に商品が販売停止になった |

## フォルダ構成

```
server/
  src/index.js        Cloudflare Workers の入口
  src/app.js          ルーティング・CORS・エラー処理（handle(request, env, ctx)）
  src/checkout.js     商品データの配信・注文・決済状況・Webhook
  src/orders.js       注文データの組み立て、支払い済み／失効の処理、定期処理
  src/admin.js        管理用 API（パスワード確認・商品データ・注文）
  src/images.js       商品画像（R2）
  src/stripe.js       Stripe API の呼び出しと Webhook 署名の確認（SDK なし）
  src/validate.js     注文フォームの入力チェック
  src/db.js           D1 への読み書き
  src/http.js         共通の小さな部品
  src/core.js         ../../js/core.js（ショップと共通の計算）を読み込む
  migrations/         D1 のテーブル定義
  dev/                ローカル用：まとめて起動（serve.mjs）、SQLite 版 D1、擬似 Stripe、R2 の代わり
  test/               自動テスト（node --test）
  wrangler.toml       Cloudflare の設定（秘密の値は書かない）
  .dev.vars.example   ローカル用の設定の見本
```

## ローカルで試す（インストール不要）

Node.js 22.13 以上が必要です（`node --version` で確認）。

```sh
# リポジトリのいちばん上のフォルダで
node server/dev/serve.mjs
```

次のものがまとめて起動します。

| | URL |
| --- | --- |
| ショップ | http://127.0.0.1:8790/shop.html |
| 管理画面 | http://127.0.0.1:8790/admin/ （パスワード `dev-admin-token-please-change-this`） |
| API | http://127.0.0.1:8787 |
| 擬似 Stripe | http://127.0.0.1:12111 |

1. ショップで商品をカートに入れ、購入手続きに進みます
2. 「注文を確定する」を押すと、**ローカルの擬似 Stripe** の画面に移ります（本物の決済ではありません）
3. 「テスト決済する」を押すとショップの完了画面に戻り、管理画面の注文一覧に「支払い済み」で出ます。「キャンセル」を押すと確認画面に戻ります

- ショップのファイルはそのまま配信されます。`/js/config.js` だけ、API を向くように差し替えて配信します（ファイル自体は書き換えません）
- データは `server/.dev/dev.sqlite` に保存されます。最初からやり直すときは `server/.dev/` を削除してください（テーブルの追加・変更は起動時に自動で反映されます）
- ポートを変えるとき：`API_PORT=8887 SITE_PORT=8890 STRIPE_PORT=12211 node server/dev/serve.mjs`

### Stripe のテストモードで試す

本物の Stripe 画面で試すときは、`server/.dev.vars.example` を `server/.dev.vars` にコピーして、テスト用のキーを入れます。

```sh
# 別のターミナルで（Stripe CLI が必要）
stripe listen --forward-to localhost:8787/api/stripe/webhook
# 表示される whsec_... を .dev.vars の STRIPE_WEBHOOK_SECRET に入れてから
node server/dev/serve.mjs
```

カード番号 `4242 4242 4242 4242`、有効期限は未来の日付、セキュリティコードは任意の 3 桁で支払えます。
本番用のキー（`sk_live_`）ではローカル起動しないようにしてあります。

## 本番に公開する（Cloudflare）

必要なもの：Cloudflare のアカウント、Stripe のアカウント、Node.js。

```sh
cd server
npm install                       # wrangler（Cloudflare のコマンド）が入ります
npx wrangler login
```

1. **データベースを作る**
   ```sh
   npx wrangler d1 create mangetsumai
   ```
   表示された `database_id` を `wrangler.toml` の `REPLACE_WITH_YOUR_D1_DATABASE_ID` と置き換えます。
   ```sh
   npx wrangler d1 migrations apply mangetsumai --remote
   ```
   `migrations/` にファイルが増えたとき（サーバーを更新したとき）も、公開の前にこのコマンドをもう一度実行してください。
2. **（任意）商品画像の保存先を作る**
   ```sh
   npx wrangler r2 bucket create mangetsumai-images
   ```
   `wrangler.toml` の `[[r2_buckets]]` の 3 行のコメント（`#`）を外します。作らない場合、管理画面から画像はアップロードできません（API は 501 `images_unavailable` を返します）。
3. **サイトの URL を設定する**：`wrangler.toml` の `[vars]`
   - `SITE_URL`：ショップの URL（最後の `/` なし）。例 `https://playmark0227-svg.github.io/mangetsumai-preview`
   - `ALLOWED_ORIGINS`：API を呼んでよいサイトのオリジン（`https://ドメイン` まで。パスは入れない。複数はカンマ区切り）
4. **秘密の値を登録する**（`wrangler.toml` には書きません）
   ```sh
   npx wrangler secret put STRIPE_SECRET_KEY      # まずはテスト用 sk_test_...
   npx wrangler secret put ADMIN_TOKEN            # 管理画面のパスワード（32文字以上・英数字と記号・空白なし）
   ```
   パスワードは次のコマンドで作ってください（32 文字のでたらめな文字列になります）。人が考えた短いパスワードは推測されるおそれがあるため、32 文字未満だと管理画面は使えません。
   `node -e "console.log(require('crypto').randomBytes(24).toString('base64url'))"`
5. **公開する**
   ```sh
   npx wrangler deploy
   ```
   表示された URL（例 `https://mangetsumai-api.xxxx.workers.dev`）の `/api/health` を開き、`{"ok":true}` が出れば動いています。
6. **Stripe の Webhook を登録する**（Stripe ダッシュボードの「ワークベンチ」→「Webhook」タブ。https://dashboard.stripe.com/webhooks ）
   1. 「**イベント送信先を作成**」を押し、「**アカウント**」を選びます
   2. ペイロード形式は必ず「**Snapshot**」を選びます。「Thin」には「推奨」と表示されますが、このサーバーは Snapshot を前提にしています（Thin で届いた場合も Stripe に問い合わせて処理はしますが、毎回の問い合わせが増え、ログに警告が出ます）
   3. API バージョンは **`2026-09-30.endive`** を選びます（サーバーが Stripe に送る `Stripe-Version` と同じ。`STRIPE_API_VERSION` を設定した場合はその値）
   4. イベントは次の 4 つを選びます：`checkout.session.completed`、`checkout.session.async_payment_succeeded`、`checkout.session.async_payment_failed`、`checkout.session.expired`
   5. 「続行」→ 送信先のタイプは「**Webhook エンドポイント**」→「続行」→ エンドポイント URL に `https://（Worker の URL）/api/stripe/webhook` を入れて作成します
   6. 作成した送信先のページで「**シークレットを表示**」を押し、署名シークレット（`whsec_...`）をコピーして登録します
   ```sh
   npx wrangler secret put STRIPE_WEBHOOK_SECRET
   ```
7. **サイトを本番モードにする**：`js/config.js` の `apiBase` に Worker の URL を入れて、サイトを公開し直します
8. **テスト決済**：カード `4242 4242 4242 4242` で 1 件注文し、管理画面の注文一覧に「支払い済み」で出ること、Stripe ダッシュボードの「支払い」に出ることを確かめます。3Dセキュアの確認は `4000 0027 6000 3184` で試せます

`wrangler dev` でも動きます（その場合は `npx wrangler d1 migrations apply mangetsumai --local` を先に実行し、`.dev.vars` に `SITE_URL` などを入れてください）。

## 本番の受付を始める前のチェックリスト

- [ ] Stripe アカウントの有効化（事業者情報・本人確認・入金先口座）。審査ではサイトの**特定商取引法に基づく表記**（販売事業者・所在地・連絡先・返品の扱いなど）が必要です。今は「（準備中）」の項目があるので埋めてください
- [ ] 本番用キー `sk_live_...` を `STRIPE_SECRET_KEY` に登録し直す（本番用キーのあいだは、テストモードの支払いが届いても注文は「支払い済み」になりません。下の「テスト決済」を参照）
- [ ] Stripe を本番環境に切り替えて Webhook エンドポイントを**もう一度**登録し（手順 6 と同じく Snapshot・`2026-09-30.endive`）、本番用の `whsec_...` を `STRIPE_WEBHOOK_SECRET` に登録し直す（テスト用とは別の値です）。テスト中の未決済の注文は、キーを切り替えたあとの定期処理で「失効」になります
- [ ] Stripe ダッシュボードで、お客さまへの**領収書メール**（支払い成功時）をオンにする。このサーバーはメールを送りません
- [ ] Stripe ダッシュボードの通知設定で、**支払いがあったときにお店に通知**が届くようにする
- [ ] カード明細に出る表記（明細書表記）を設定する
- [ ] `SITE_URL`・`ALLOWED_ORIGINS` を実際のドメインにする（独自ドメインに移るときも忘れずに）
- [ ] `ADMIN_TOKEN` を上のコマンドで作った 32 文字以上のものにする（同じ接続元から 15 分の間に 10 回試すと、15 分ロックされます。同時にまとめて送られた場合も 10 回までしか確かめません。IPv6 は /64 ごとに数えます）
- [ ] 回数制限はサーバーに組み込み済みです（同じ接続元から 1 分あたり、注文 30 回・決済状況の確認 120 回・決済画面の取り消し 120 回まで。下の「回数制限」を参照）。高輪のイベントでは、会場の Wi-Fi や携帯電話の回線で何百台ものスマートフォンが同じ接続元になるため、多めにしてあります。超えた場合も、同じ接続元のお客さまが待つのは最長 1 分です。さらに守るなら Cloudflare の WAF のレート制限ルールを `/api/checkout` と `/api/admin/*` にかけます（任意。かける場合も、同じ接続元からの多数のお客さまを止めない値にしてください）。Cloudflare Access を使う場合は、管理画面を API と同じドメインで配信するなどの工夫が必要です（管理画面は Cookie を送らずに API を呼ぶため）
- [ ] 本番の商品データ・価格・送料表・在庫を管理画面で確認する
- [ ] 高輪のイベントの前に、在庫数を入れる商品を決める。十分な数を用意できる商品は、イベントの間は在庫数を**空欄**（在庫を管理しない）にしておくと、取り置きで待たされることがありません。`HOLD_PER_CLIENT` は既定（上限なし）のままにし、いたずらが見られたときだけ設定します（下の「在庫の取り置き」）
- [ ] （任意）`HOLD_SALT` を登録する（`npx wrangler secret put HOLD_SALT`。作り方は `ADMIN_TOKEN` と同じ）。登録しなければ `ADMIN_TOKEN` を使います。決済画面の有効期限を変えるときは `SESSION_MINUTES`（下の「設定」）
- [ ] 1 件、実際のカードで少額の注文 → Stripe で返金、まで通して確かめる
- [ ] Cloudflare Workers は **Paid プラン（月 5 ドル）を推奨**。無料プランは 1 リクエストあたりの CPU 時間が短く、商品データが大きいと処理が打ち切られることがあります
- [ ] **定期便**は、このサーバーでは受け付けません（Stripe Billing での定期課金の作り込みが必要）。カートに入っていると注文できない（400 `subscription_not_supported`）ので、商品は「非公開」のままにしてください

## 在庫・注文・返金のしくみ

- **金額**：商品の値段・送料・合計は、すべてサーバーが D1 の商品データと送料表で計算し直します。ブラウザから送られた金額は使いません。送料は配送先（別の住所に届ける場合はそちら）の都道府県で決まります。重さで 30kg までの箱に詰め（重い順）、箱ごとに重さの区分の料金を足します。Stripe の決済画面では、送料はショップと同じ書き方で「送料（関東）」「送料（関東・2箱）」（2 箱以上のとき）、無料なら「送料無料」と出ます
- **表示した合計との食い違い**：ショップは、確認画面に表示したお支払い合計を `expectedTotal`（整数）として注文と一緒に送ります。サーバーで計算した合計と違うとき（ページを開いたあとに価格や送料表が変わった場合など）は、注文も決済画面も作らずに 409 `price_changed`（`details: { total }`＝サーバーの合計）を返します。ショップは最新の商品データを読み込み直し、新しいお支払い合計で確認画面を表示し直して、お客さまにもう一度「注文を確定する」を押してもらいます。`expectedTotal` は比べるためだけのもので、請求には使いません（送られていない・整数でないときは比べません）
- **在庫**：管理画面で在庫数を入れた商品だけが対象です。購入手続きの時点で在庫と数量の上限を確かめ、**支払いが済んだ時点で**在庫を減らします。Webhook が 2 回届いても、在庫が減るのは 1 回だけです
- **在庫の取り置き**：在庫数を入れた商品は、ほかのお客さまが決済画面に進んでいる数量（未決済の注文のうち、作成から「決済画面の有効期限＋10 分」＝既定 40 分以内で決済画面のあるもの）を在庫から差し引いて、残りだけを受け付けます。足りないときは注文も決済画面も作らずに 409 `cart_changed` を返します（`details` は売り切れ・在庫不足と同じ形）。ショップはカートの数量を合わせるか、カートから外すか、そのままにして、その旨をお知らせします

  | `details` の `code` | 意味 | `max` |
  | --- | --- | --- |
  | `stock` | 在庫数そのものが足りない（決済画面を作っている間に管理画面で在庫数が減らされた場合など） | 注文できる数（取り置き中の分を除く） |
  | `held` | 在庫数は足りているが、ほかのお客さまの決済画面で取り置き中の分を除くと足りない（残りがすべて取り置き中なら `max: 0`）。または、`HOLD_PER_CLIENT` を設定していて、同じ接続元がすでに上限まで取り置いている（下を参照） | いま注文できる数（`0` なら、しばらくおいてからもう一度。支払われなければ戻ります） |
  | `sold_out` | 在庫が 0（取り置きの確認中に支払いが済んだなど） | なし |

  - **同じ接続元が取り置ける数（`HOLD_PER_CLIENT`）**：既定は**上限なし**（`0`）です。在庫数から取り置き中の分を除いた残りまでなら、同じ接続元（IP アドレス。IPv6 は /64 ごと）からいくつでも決済画面に進めます。高輪のイベントのように、会場の Wi-Fi や携帯電話の回線で何百台ものスマートフォンが同じ接続元になる場合に、同じ接続元のほかのお客さまの取り置きのせいで止まらないようにするためです
    - 上限なしの弱点：決済画面を開いては支払わずに放置することをくり返せば、1 人でも在庫を取り置きでふさいで、ほかのお客さまに「お支払い手続き中」（`held`）と見せられます（1 件あたり最長「有効期限＋10 分」＝既定 40 分。1 件で取り置けるのは 1 回のご注文の上限数 `maxQty` まで、件数は注文の回数制限 `LIMIT_CHECKOUT`＝1 分 30 回まで）
    - `HOLD_PER_CLIENT` に 1 以上の整数を入れると、1 つの接続元が取り置けるのは 1 種類につきその数までになり、超える注文は 409 `cart_changed`（`code: 'held'`、`max`＝あと取り置ける数）になります（同時にまとめて送られても超えません）。そのかわり、会場の Wi-Fi など同じ接続元のお客さま**全員で**その数を分け合うことになり、在庫数を入れた同じ商品を同時に決済画面で開いていられるのは、会場全体でその数までになります（支払いが済む・戻る・期限が切れると空きます）。会場から大勢が同じ商品を買うと、在庫は残っているのに多くのお客さまが「お支払い手続き中」（`held`）で断られます
    - **イベントのときのおすすめ**：十分な数を用意できる商品は、イベントの間は管理画面の在庫数を**空欄**（在庫を管理しない＝取り置きもしない）にしておきます。数に限りがあって在庫数を入れる商品も、`HOLD_PER_CLIENT` は既定（上限なし）のままにし、いたずらが見られたとき（管理画面の注文一覧を「決済待ちの注文」に切り替えると支払われない注文が短い間に大量に並んでいる、在庫は残っているのにお客さまから「手続き中で買えない」と言われる、など）だけ設定してください（例：`wrangler.toml` の `[vars]` に `HOLD_PER_CLIENT = "20"` と書いて `npx wrangler deploy`。やめるときは行を消すか `"0"` にして公開し直します）
    - 在庫を管理しない商品（在庫数が空欄）には、どちらの場合も関係ありません
  - 接続元は、IP アドレスそのものではなく、秘密の値（`HOLD_SALT`、なければ `ADMIN_TOKEN`）を使ったハッシュ（HMAC-SHA256）で注文に残し（D1 の `orders.client_key`。管理画面には出ません）、作成から 1 日たつと定期処理で消します。`HOLD_PER_CLIENT` が `0`（上限なし）のときも残します（あとから設定したとき、すでに開いている決済画面の分も数えるため）。`HOLD_SALT` も `ADMIN_TOKEN` もないときは、`HOLD_PER_CLIENT` を設定していても接続元ごとには数えません（ログに 1 回警告）
  - 取り置きが終わるのは、支払いが済んだとき（在庫が減る）、お客さまが支払わずに戻って決済画面が取り消されたとき、決済画面の有効期限が切れたとき、または作成から「有効期限＋10 分」たったとき（Webhook が届かなくても）です
  - 決済画面を作っている最中の注文（Stripe の返事を待っている間）も、2 分間は取り置きに数えます。最後の 1 点に同時に複数の注文が来ても、先に保存された 1 件だけが決済画面に進みます（ほかは 409。そのとき保存されていた注文は「失効」として残ります）
  - **決済画面を作っている間の変更**：Stripe が決済画面を作っている間（ふつう 1 秒ほど。混み合うと数秒）に、管理画面で商品が「売り切れ」「非公開」・削除・在庫数 0 にされた場合や、最後の在庫が支払われた場合、その注文にはまだ決済画面の ID が保存されていないため、開いている決済画面を閉じる処理（下の「最後の在庫が売れたとき」「販売停止後の決済」）では見つかりません。そこで、決済画面ができて ID を保存したあとに、その時点の商品データでカートをもう一度確かめます。販売できなくなった商品があれば、お客さまに決済画面の URL を渡さずに 409 `cart_changed`（`code` は `sold_out` または `not_found`）を返します。在庫数を入れた商品は取り置きも確かめ直し、その間に在庫数が減らされて足りなくなった場合も 409（`held` または `stock`）です。そのとき作った決済画面は Stripe で閉じ（返事のあとに行います。Stripe に届かなくても、URL はだれにも渡っていないので支払われることはなく、有効期限で切れます）、注文は「失効」になります
  - 取り置きは在庫数そのものは変えません（管理画面の在庫数は、支払い済みの分だけ減ります）。お客さまが決済画面を開いたまま閉じた場合、その数量は最長 40 分ほど（既定の場合）買えない状態になります
- **決済画面の有効期限**：`SESSION_MINUTES`（分。30〜1440 の整数、既定 30＝Stripe が受け付ける最短）。Stripe は決済画面を作った時刻から数えて 30 分未満を受け付けないため、Stripe に送る期限はこれより 2 分遅くしています（1440 のときは 24 時間より 2 分短く）。範囲外の値はいちばん近い値（30 または 1440）に、数でない値は 30 にして、ログに一度だけ警告を出します。変えた値は、変えたあとの注文から使われます
- **最後の在庫が売れたとき**：支払いで在庫が 0 になった商品について、ほかに開いている決済画面（管理画面で在庫を減らした場合などに残ることがあります）を Stripe で閉じ、その注文を「失効」にします。Stripe に届かなくても Webhook の処理は失敗させません（決済画面は有効期限で切れます）
- **売り違い**：取り置きをしていても、お客さまが決済画面にいる間に管理画面で在庫数を減らした場合や、上の「閉じる」処理が Stripe に届かなかった場合などは、支払い時に在庫が足りないことがあります。そのときは在庫は 0 で止まり、注文に `stockShort`（足りなかった数）が記録されます。お客さまに連絡し、必要なら返金してください
- **販売停止後の決済**：お客さまが決済画面にいる間に、管理画面で商品を「売り切れ」「非公開」にした・商品（または種類）を削除した・在庫数を 0 にした場合、保存したあとで、その商品を含む開いている決済画面を Stripe で閉じ、注文を「失効」にします（Cloudflare では保存の返事のあとに行うので、保存は待たされません。Stripe に届かなくても保存は失敗しません）。閉じるのは**新しい決済画面から順に**（いま支払おうとしているお客さまほど先に）、100 件ずつ、残りがなくなるまでです。Cloudflare が返事のあとに処理を続けられる時間（約 30 秒）のうち 20 秒を使い切ったら、残りは閉じずに件数をログに残します（`[expire] {"expired":…,"failed":…,"left":…,"batches":…,"stopped":true,"more":false}`。`expired` は閉じた件数、`failed` は Stripe に届かなかった件数、`left` は閉じられずに残った件数です。`left` には、まだ見ていなかった分もデータベースだけで数えて入れます（Stripe は呼びません）。数えるのにさらに 3 秒まで使い、それでも数え終わらないときは `"more":true` になり、`left` は「少なくともこの件数」です。残りは有効期限で切れ、支払われた場合は下の `unavailable` が記録されます）。最後の在庫が売れたときも同じです。保存した瞬間にまだ決済画面を作っている最中だった注文は、上の「決済画面を作っている間の変更」で止まります。閉じる前に支払いが済んでしまった場合や、Stripe に届かずに支払われた場合も、お金を受け取っているので注文は「支払い済み」になり、`unavailable: [{ pid, vid, name, reason }]`（`reason` は `soldout`＝売り切れ・`draft`＝非公開・`deleted`＝削除）が記録されます。管理画面では「**販売停止後の決済**」と表示されます。発送できるか確かめ、できなければお客さまに連絡して返金してください（在庫数を 0 にした場合は、`stockShort` として記録されます）
- **テスト決済**：注文には、支払いが本番（`stripe.livemode: true`）かテストモード（`false`）かを記録します。テストモードの支払い（カード `4242…`、お金は動きません）の注文は、管理画面で「**テスト決済**」と表示されます。発送しないでください。`STRIPE_SECRET_KEY` が本番用（`sk_live_` / `rk_live_`）のときにテストモードの支払い（`livemode` が `true` でないもの。項目がない・文字列の場合も含みます）が届いた場合（テスト用の決済画面がまだ開いているうちにキーを切り替え、`STRIPE_WEBHOOK_SECRET` がテスト用のままだった場合など）は、注文を「支払い済み」にせず未決済のままにし、ログに警告（お客さまの情報は含みません）を残して、Webhook には 200 を返します。その注文は定期処理で「失効」になります
- **金額の不一致**：Stripe で支払われた金額（または通貨）が注文の合計と違う場合（通常は起きません）、注文は支払い済みのまま `amountMismatch: { expected, received, currency }` が記録されます。管理画面では、注文一覧の「お支払い」の欄とダッシュボードの最近の注文に「**金額不一致**」と表示され、注文の詳細に受け取った金額と注文の合計が出ます。発送の前に Stripe ダッシュボードで確認してください
- **返金**：Stripe ダッシュボード → 支払い → 該当の支払い → 返金。そのあと管理画面で注文を「キャンセル」にしてください。**在庫は自動では戻りません**。必要なら管理画面で在庫数を直してください
- **Webhook が届かなかったとき**：お客さまが完了画面を開いたとき、および 30 分ごとの定期処理で、サーバーが Stripe に直接問い合わせて注文を確定（または失効）させます。Stripe がその決済画面を知らない注文（テスト用のキーから本番用のキーに切り替えたあとのテストの注文など）は「失効」にします。あとから支払い済みの Webhook が届けば「支払い済み」になります
- **支払わずに戻ったとき**：決済画面は、そのままだと有効期限（既定 30 分）まで支払えてしまい、あとで別の注文と二重に支払われるおそれがあります。そこでショップは、`POST /api/checkout` が返す `sessionId` をそのタブに覚えておき、`POST /api/checkout/cancel`（`{ session_id }`）で前の決済画面を Stripe で無効にします（注文は「失効」になります）。呼ぶのは次のときです
  - 支払わずにショップに戻ってきたとき（決済画面の「戻る」で `?canceled=1` 付きで戻ったとき、ブラウザの「戻る」で戻ったとき）
  - もう一度「注文を確定する」を押したとき。新しい決済画面を作る**前に**前の決済画面を無効にし、無効にできたと分かるまでは新しい注文を作りません（「前回のお支払い画面を閉じられませんでした。…」と表示）。前の決済画面がじつは支払い済みだった場合（別のタブで支払ったなど）は、新しい注文は作らずにその注文の完了画面を表示します
  - 注文は作れたものの、サーバーの合計が表示していた合計と違ったとき（決済画面には進まず、その場で無効にします。ふつうは `expectedTotal` で 409 `price_changed` になるので、念のための処理です）

  すでに支払い済みの注文は変えず、`payment: 'paid'` を返します。サーバーが知らないセッション（404）は、支払えるものがないので、ショップは閉じたものとして扱います。ログインは不要で、推測できない長いセッション ID を知っていること（＝そのお客さまのブラウザ）が取り消しの条件です。取り消すと、その注文の在庫の取り置きも終わります。取り消しが届かなかった場合も、決済画面は有効期限で切れ、注文は Webhook か定期処理で「失効」になります
- **同じご注文のやり直し（二重払いの防止）**：同じお客さまが別のブラウザ（スマートフォンとパソコンなど）で、またはブラウザのデータを消したあとで同じご注文をやり直すと、前の決済画面はそのブラウザからは取り消せず、両方で支払えてしまいます。そこで `POST /api/checkout` は、新しい注文を保存する**前に**、次の 3 つがすべて同じ未決済の注文（作成から「有効期限＋10 分」以内で決済画面のあるもの）を探して、その決済画面を Stripe で閉じます（注文は「失効」）
  - メールアドレス（前後の空白を除き、大文字・小文字は区別しない）
  - 商品・種類・数量の組み合わせ（カートの並び順は問わない）
  - お届け先の住所（別の住所に届ける場合はそちら。郵便番号・都道府県・住所。全角・半角、空白、ハイフンの種類の違いは同じとみなします。お名前は比べません）

  閉じられなかった場合（Stripe に届かないなど）も新しい注文は作ります（ログに警告）。閉じようとした決済画面がじつは支払い済みだった場合（Webhook がまだ届いていない）は、その注文を「支払い済み」にします。そのうえで、同じ 3 つの注文が **60 分以内に支払い済み**になっていれば（管理画面で「キャンセル」にしたものを除く）、新しい注文は作らずに 409 `duplicate_paid`（`error`＝「同じ内容のご注文（ご注文番号 MG-…）のお支払いが、すでに完了しています。…」、`details: { orderNo, paidAt }`）を返します。金額は返しません（メールアドレス・商品と数量・お届け先の 3 つを知っている人には、ご注文番号と支払った時刻までは分かります）。お客さまが確認のうえ、もう一度ご注文になるときは、ショップが `confirmDuplicate: true` を付けて送り直すと注文できます（`confirmDuplicate` は `true` / `false` のみ。ほかの値は 400 `invalid`）。照合には、この 3 つから作ったハッシュ（D1 の `orders.dup_key`）を使います
  - **ほぼ同時の場合**：Stripe が決済画面を作っている間（ふつう 1〜2 秒）に別のブラウザから同じご注文が来ると、どちらもまだ相手の決済画面が見えません。そこで、決済画面を作り終えて保存したあとに、同じ 3 つの未決済の注文をもう一度探し、**あとから始めた（あとに保存された）注文だけを残します**。自分よりあとの注文がすでに決済画面を持っていれば、自分の決済画面は URL を渡さずに Stripe で閉じ、注文を「失効」にして 409 `duplicate_pending`（`error`＝「同じ内容のご注文の手続きが、ほかの画面で進んでいます。そちらの画面でお支払いを完了してください。」、`details` なし）を返します。自分より前の注文があれば、その決済画面を閉じます（上と同じく、閉じられなかった場合もログに警告を残して進みます。閉じようとした決済画面が支払い済みだった場合は、上と同じ 409 `duplicate_paid`）。どちらが先に終わっても、支払えるのはあとから始めた 1 件だけです
- **回数制限**：同じ接続元（IP アドレス。IPv6 は /64 ごと）から **1 分あたり**に受け付ける回数です。高輪のイベントのように、会場の Wi-Fi や携帯電話の回線（CGNAT）で何百台ものスマートフォンが同じ接続元になっても止まらないよう多めにしてあり（10 分あたりにすると以前と同じ 300 回・1,200 回・1,200 回）、いたずらで大量に送られた場合だけ止まります。1 分ごとに数え直すので、だれかが上限まで使ってしまっても、同じ接続元のほかのお客さまが待つのは最長 1 分です。それぞれ別に数えるので、完了画面での決済状況の確認が多くても、新しい注文の前に必要な取り消しが止められることはありません。値は環境変数で変えられます（下の「設定」）

  | 対象 | 既定値（1 分あたり） | 環境変数 | 超えたとき |
  | --- | --- | --- | --- |
  | 注文（`POST /api/checkout`。入力エラー・価格の変更・売り切れなどで断ったものは数えません。取り置き `held`・同じご注文 `duplicate_paid` / `duplicate_pending`・決済画面を作ったあとの確認で断ったものは数えます） | 30 回 | `LIMIT_CHECKOUT` | 429 `too_many_requests`（`Retry-After: 60`、「1分ほどおいて…」）。注文番号は使いません |
  | 決済状況の確認で Stripe に問い合わせる回数（`GET /api/checkout/status`） | 120 回 | `LIMIT_STATUS` | Stripe に問い合わせず、保存済みの状態を返します（ショップは少しおいて、また確かめます） |
  | 決済画面の取り消しで Stripe を呼ぶ回数（`POST /api/checkout/cancel`。すでに閉じた注文は数えません） | 120 回 | `LIMIT_CANCEL` | 429 `too_many_requests`（`Retry-After: 60`） |

  管理画面のパスワードのロック（15 分の間に 10 回まで）は別のしくみで、変わりません
- **注文番号**：`MG-年月日-8桁の数字`（例 `MG-261012-48213907`）。支払われなかった注文も番号を使うため、1 日に足りなくならないよう 8 桁にしています（以前の 4 桁の番号もそのまま使えます）
- **郵便番号と都道府県**：送料は都道府県で決まるため、ご住所の食い違いを 2 とおりで確かめます（ご注文者さまの住所と、別の住所に届ける場合はお届け先の住所）
  - **市区町村の欄が別の都道府県名で始まる**（例：都道府県は北海道、市区町村は「沖縄県那覇市…」）：確実に食い違っているので受け付けません（400 `invalid`、`details` の `field` は `customer.addr1` / `shipTo.addr1`）。「東京都」「北海道」のように都・道・府・県まで含む名前が先頭にあるときだけで、選んだ都道府県名をくり返して書くのはかまいません（例：東京都を選んで「東京都港区…」）。「京都市」「愛知郡（滋賀県）」のような地名では止まりません
  - **郵便番号の上 3 桁が別の都道府県のもの**（例：沖縄の郵便番号で北海道を選ぶ）：受け付けたうえで、注文に注意書き `addressWarnings: [{ who: 'customer' | 'shipTo', code: 'zip_pref_mismatch', zip, pref, expected: ['沖縄県'] }]` を記録します（`expected` はその郵便番号のふつうの都道府県。注意書きがない注文にはこの項目自体がありません）。郵便番号の表（`src/zip.js`）は記憶をもとに作ったもので、日本郵便のデータとはまだ突き合わせていない（確認できたのは 618 だけ）ため、表の誤りで本当のお客さまの注文を止めないよう、止めずに記録だけにしています。送料は選ばれた都道府県で計算されます。管理画面では、注文一覧とダッシュボードの最近の注文に「**住所を確認**」と表示され、注文の詳細にどの住所のどの郵便番号かが出るので、発送の前にお客さまに確認してください。2 つの県にまたがる番号（498・618・684・685・871）はどちらの県でも注意書きは付かず、表にない番号は確かめません
- **イベント経由の注文**：高輪イベントのページから来たお客さまの注文は、イベントが有効な期間（日本時間）の間だけ「イベント経由」として記録され、お届け希望日は付きません。予約商品を含む注文も同じです（送られてきた希望日はサーバーで空にします）
- **メール**：このサーバーはメールを送りません。お客さまへの領収書は Stripe から、お店への通知も Stripe の設定で受け取ります
- **バックアップ**：`npx wrangler d1 export mangetsumai --remote --output backup.sql`。D1 の Time Travel 機能で過去の時点に戻すこともできます

## API 一覧

すべて JSON。エラーは `{ error: '日本語のメッセージ', code: '...', details?: ... }` と HTTP ステータスで返します。

| メソッド・パス | 内容 |
| --- | --- |
| `GET /api/health` | 動作確認 → `{ ok: true }` |
| `GET /api/catalog` | 公開中・売り切れの商品データ → `{ catalog, rev }` |
| `POST /api/checkout` | 注文 → `{ orderNo, url, total, sessionId }`（`url` は Stripe の決済画面。`sessionId` は取り消し用にショップが覚えておく）。任意で `expectedTotal`（整数）・`confirmDuplicate`（`true` / `false`）を送れます。郵便番号と都道府県が合わないときはエラーにせず、注文に `addressWarnings` を記録します（返す内容は同じ）。400 `invalid`（`details: [{ field, message }]`、`field` は `customer.zip` などの形）、409 `cart_changed`（`details: [{ pid, vid, code, name, max? }]`。`code` は `sold_out`・`stock`・`qty`・`not_found`、取り置きで足りないときは `held`。上の「在庫の取り置き」。決済画面を作ったあとの確認で断る場合も同じ形）、409 `price_changed`（任意で送る `expectedTotal`＝ショップが表示したお支払い合計とサーバーの合計が違うとき。`details: { total }`）、409 `duplicate_paid`（同じご注文が 60 分以内に支払い済み。`details: { orderNo, paidAt }`。`confirmDuplicate: true` で注文できる）、409 `duplicate_pending`（ほぼ同時に別の画面で始めた同じご注文があり、そちらを残した。`details` なし）、400 `subscription_not_supported`、429 `too_many_requests`（`Retry-After` 付き）、503 `payments_unavailable`、502 `stripe_error` |
| `GET /api/checkout/status?session_id=cs_...` | 完了画面用 → `{ orderNo, payment, name, total, preorder, mixed, preorderShip, eventNote }`。未知のセッションは 404。同じ接続元からの問い合わせが多すぎるとき（`LIMIT_STATUS`）は Stripe に問い合わせず、保存済みの状態を返します |
| `POST /api/checkout/cancel` | `{ session_id: 'cs_...' }` → その決済画面を Stripe で無効にして、`status` と同じ形で返す（`payment` は通常 `expired`。すでに支払い済みならそのまま `paid`）。未知のセッションは 404、Stripe に届かないときは 502、多すぎると（`LIMIT_CANCEL`）429 |
| `POST /api/stripe/webhook` | Stripe からの通知（署名を確認。不正なら 400） |
| `GET /api/admin/session` | 管理用パスワードの確認 → `{ ok: true }` |
| `GET /api/admin/catalog` | 非公開を含む商品データ → `{ catalog, rev }` |
| `PUT /api/admin/catalog` | `{ catalog, rev }` を保存 → `{ catalog, rev }`。`rev` が古いと 409 `conflict`（`details` に最新の `{ catalog, rev }`）、大きすぎると 413 `too_large`。保存したあと、売り切れ・非公開・削除・在庫 0 になった商品を含む開いている決済画面を Stripe で閉じます（Stripe に届かなくても保存は成功します） |
| `GET /api/admin/orders?payment=paid\|pending\|expired\|all` | 注文一覧（新しい順・最大 1000 件、既定は `paid`）→ `{ orders }`。確認が必要な注文には `addressWarnings`（住所を確認）・`amountMismatch`（金額不一致）・`stockShort`（在庫不足）・`unavailable`（販売停止後の決済：`[{ pid, vid, name, reason: 'soldout'\|'draft'\|'deleted' }]`）が付きます（ないときは項目自体がありません）。支払い済みの注文の `stripe.livemode` が `false` ならテストモードの支払い（テスト決済）です（以前の注文には項目がありません） |
| `PATCH /api/admin/orders/:no` | `{ status: 'new'\|'preparing'\|'shipped'\|'canceled' }` → `{ order }` |
| `POST /api/admin/images` | 画像（WebP・JPEG・PNG、2MB まで。本文にそのまま）→ `{ url }`。R2 がないと 501 `images_unavailable` |
| `GET /api/images/<key>` | 画像の配信（1 年間キャッシュ） |

管理用 API はすべて `Authorization: Bearer <ADMIN_TOKEN>` が必要です。違うと 401 `unauthorized`、`ADMIN_TOKEN` が未設定または 32 文字未満のときは 503 `admin_unavailable`（管理用 API は一切使えません）、続けて間違えると 429 `too_many_attempts` です。

## 設定（環境変数・バインディング）

| 名前 | 種類 | 内容 |
| --- | --- | --- |
| `DB` | D1 | 商品データ・注文 |
| `IMAGES` | R2（任意） | 商品画像 |
| `STRIPE_SECRET_KEY` | secret | Stripe のシークレットキー（`sk_test_` / `sk_live_`）。ないと注文は 503 |
| `STRIPE_WEBHOOK_SECRET` | secret | Webhook の署名シークレット（`whsec_`） |
| `ADMIN_TOKEN` | secret | 管理画面のパスワード（32 文字以上） |
| `SITE_URL` | var | ショップの URL（決済後・キャンセル後の戻り先） |
| `ALLOWED_ORIGINS` | var | API を呼べるサイトのオリジン（カンマ区切り） |
| `STRIPE_API_VERSION` | var（任意） | Stripe API のバージョン。未設定なら `src/stripe.js` の固定値 `2026-09-30.endive` を毎回送ります（アカウントの既定のバージョンには左右されません）。変えるのは、Stripe の Webhook エンドポイントのバージョンも合わせるときだけ |
| `STRIPE_API_BASE` | var（開発用） | 擬似 Stripe に向けるときだけ使います。本番用キー（`sk_live_`）と一緒に Stripe 以外を指定すると、キーを外に送らないよう決済をエラーにします |
| `SESSION_MINUTES` | var（任意） | Stripe の決済画面の有効期限（分）。30〜1440 の整数、既定 `30`。在庫の取り置きはこれ＋10 分 |
| `HOLD_PER_CLIENT` | var（任意） | 同じ接続元が 1 種類につき取り置ける数。0 以上の整数、既定 `0`＝上限なし（イベント会場のように大勢が同じ接続元から買えるように）。いたずらが見られたときだけ設定します（上の「在庫の取り置き」） |
| `HOLD_SALT` | secret（任意） | 注文に残す接続元の印（IP アドレスの HMAC-SHA256）に使う秘密の値。未設定なら `ADMIN_TOKEN` を使います。作り方は `ADMIN_TOKEN` と同じ。変えると、その時点で取り置き中の分は接続元ごとに数え直しになります（最長「有効期限＋10 分」の間だけの影響です） |
| `LIMIT_CHECKOUT` | var（任意） | 同じ接続元から 1 分あたりの注文の回数。既定 `30` |
| `LIMIT_STATUS` | var（任意） | 同じ接続元から 1 分あたり、決済状況の確認で Stripe に問い合わせる回数。既定 `120` |
| `LIMIT_CANCEL` | var（任意） | 同じ接続元から 1 分あたり、決済画面の取り消しで Stripe を呼ぶ回数。既定 `120` |

`LIMIT_*` は 1 以上の整数で指定します（`wrangler.toml` の `[vars]` に `LIMIT_CHECKOUT = "500"` のように書きます。ローカルでは `.dev.vars` か環境変数）。それ以外の値は無視して既定値を使い、ログに一度だけ警告を出します。`HOLD_PER_CLIENT` は 0 以上の整数で、それ以外の値は無視して上限なしにし、ログに一度だけ警告を出します。

## ショップと共通の計算（js/core.js）の読み込み

送料・合計・商品データの検証は、ショップと同じ `js/core.js` を使っています（サーバー側に同じ計算を書き写していません）。
`js/core.js` はブラウザ用のふつうのスクリプトなので、`src/core.js` で次のように読み込んでいます。

```js
import '../../js/core.js';            // 読み込むと globalThis.MangetsuCore ができる
const Core = globalThis.MangetsuCore;
```

- Node（テスト・`dev/serve.mjs`）：`js/` の上に `package.json` がないので CommonJS として読み込まれ、実行されます
- wrangler（esbuild でひとつにまとめる）：CommonJS のモジュールとして取り込まれ、読み込み時に実行されます

`import Core from '../../js/core.js'` でも今は動きますが、将来 `js/` より上に `"type": "module"` の `package.json` が置かれると壊れるため、この書き方にしています。
`js/core.js` を変更したら、サーバーも `npx wrangler deploy` し直してください（ショップと計算がずれないように）。

## 既知の制限

- 定期便（定期課金）は未対応です。API が受け付けません
- 在庫の取り置きは、決済画面に進んだ時点から最長「有効期限＋10 分」（既定 40 分）です（在庫数そのものは支払い時に減らします）。お客さまが決済画面を開いたまま閉じた場合、その数量はしばらく買えません。同じ接続元が取り置ける数は、既定では上限がありません（`HOLD_PER_CLIENT` を設定すれば 1 種類につきその数まで。それでも IP アドレスをいくつも使い分ければ、それを超えて取り置けます。IPv6 は /64 ごとに数えます）。お客さまが決済画面にいる間に管理画面で在庫数を減らした場合などは、まれに売り違いが起き、`stockShort` が記録されます
- 同じご注文のやり直しは、メールアドレス・商品と数量・お届け先の住所がすべて同じときだけ見分けます（どれかが違えば別の注文として扱います）
- 注文の確認メールは送りません（Stripe の領収書メールを使います）
- 管理画面のパスワードは 1 つだけです（担当者ごとのログインはありません）
- 商品データは 1 つの JSON として保存しています（約 1.8MB まで）。画像は R2 に置くと小さく保てます
- 注文一覧は新しいものから 1000 件までです。注文データ（個人情報）を削除する画面はありません
- 送料表（`js/core.js` の `DEFAULT_SHIP_RATES`）で、先方に確認中のこと
  - 山梨県は表になかったため、仮に関東に入れています
  - 中国〜南九州は 20kg の料金（1,550円）が 15kg（2,090円）より安くなっています（表のとおり）
  - 表には税込・税抜の記載がありません。サイトでは**税込**として扱っています（ショップの表示も「税込」）。税抜と分かったら、各金額を 1.1 倍（1 円未満は四捨五入）にし、管理画面で保存済みの送料表も直す必要があります
- 適格請求書（インボイス）や消費税の内訳の表示には対応していません。必要な場合は Stripe の設定や別の仕組みが必要です
